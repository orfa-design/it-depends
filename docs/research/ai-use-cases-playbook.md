## Як читати цей документ

Кожен кейс розкладено на **3–5 етапів**. Кожен етап = **Дія → Інструмент → Готовий промпт → Чекпоінт** («як зрозуміти що вийшло»). Структура свідомо повторює quest-патерн з Adaline (фаза → кроки зі станами + опис + перевірка), але ми її адаптуємо під свій інтерфейс.

### Принцип шарів «level-up»
Для кожного кейсу є два шляхи:
- 🟢 **Основний (no-code)** — тільки чат + скріни + готові community-плагіни. Нульовий бар'єр для нашого casual→power юзера.
- ⚡ **Level-up (power)** — агентний Figma (MCP), Figma Make, Claude Code. Більше потужності, але потребує сетапу. Це наступний крок по карті, не перший.

### Принцип чесності (важливо для журі)
Слідуємо тезі Nielsen: **AI — це «найзеленіший стажер»**. Він швидко генерує чернетки й варіанти, але людина валідує перед використанням. Особливо це стосується E1 (критика) — див. honesty-блок там. Ми не продаємо AI як суддю; ми продаємо його як прискорювач рутини з людським чекпоінтом.

### Легенда інструментів
`Claude.ai` — чат, приймає скріни (vision) · `Figma Make` — генеративний режим Figma · `Figma agent / MCP` — агент на канвасі (beta, 2026) · `Plugin` — community-плагін Figma.

# D1 — Документація компонентів / дизайн-системи

> **Біль:** #1 запит в опитуванні (×5). Документувати компоненти руками нудно, тому це або не роблять, або роблять неконсистентно. Нема копірайтера/тех-райтера.
> **Що зможеш:** структурована дока компонента (props, стани, usage, do/don't, rationale) за ~20 хв замість години.
> **Рекомендований інструмент:** 🟢 Claude.ai · ⚡ Figma Make (AI Component Documentation Generator)
> **Час:** ≈25 хв

### Етап 1 — Зібрати контекст компонента
**Дія:** Зроби скрін компонента (всі варіанти що є) і коротко зафіксуй: як називається, де використовується, які проперті вже є.
**Інструмент:** Claude.ai (встав скрін).
**Промпт:**
```
Ти технічний райтер дизайн-системи. Я даю тобі компонент — допоможи задокументувати його.

Компонент: [назва, напр. Button]
Де використовується: [напр. форми, модалки, картки]
Що бачиш на скріні: [встав зображення]

Спочатку постав мені 3 запитання, щоб зрозуміти призначення і межі компонента. Тільки потім переходь далі.
```
**Чекпоінт:** Claude поставив запитання про призначення/межі, а не одразу почав писати. Ти відповіла — контекст є.

### Етап 2 — Згенерувати структуру доки
**Дія:** Попроси структуровану специфікацію.
**Інструмент:** Claude.ai.
**Промпт:**
```
Тепер згенеруй структуровану документацію в markdown:
— Призначення (1-2 речення)
— Anatomy (з яких частин складається)
— Props / properties (назва, тип, значення за замовчуванням, опис)
— Variants (візуальні варіації)
— States (default, hover, focus, active, disabled, error, loading, empty)
— Розміри / spacing якщо релевантно

Тільки те, що випливає з контексту. Де не знаєш — постав [?] і запитай.
```
**Чекпоінт:** Є таблиця props і повний список станів. Невідомі місця позначені `[?]`, не вигадані.

### Етап 3 — Usage guidelines + do/don't + rationale
**Дія:** Додай людську частину — коли застосовувати, коли ні, і чому.
**Інструмент:** Claude.ai.
**Промпт:**
```
Додай до документації:
— When to use / When not to use
— Do / Don't (по 3-4 конкретні приклади з нашого контексту)
— Accessibility-нотатки (контраст, фокус, клавіатура, aria-label)
— Rationale: чому компонент влаштований саме так (1 абзац)

Пиши коротко й конкретно, без води. Тон — для внутрішньої дизайн-системи команди.
```
**Чекпоінт:** Do/Don't конкретні (не «використовуйте правильно»), є a11y-нотатки.

### Етап 4 — Причесати тон і зберегти
**Дія:** Уточни тон під свою команду й винеси в постійне місце.
**Інструмент:** Claude.ai.
**Промпт:**
```
Переглянь весь текст і приведи до єдиного тону: [короткий / формальний / дружній].
Прибери повтори. Дай фінальний markdown одним блоком.
```
**Чекпоінт:** Готовий markdown, який можна вставити в Notion / Figma / репозиторій DS.

### ⚡ Level-up
- **Figma Make → AI Component Documentation Generator:** 4-кроковий вбудований флоу — даєш компонент + його UI → описуєш вимоги plain language → генерує props/states/edge cases + інтерактивні приклади (hover, focus, keyboard, validation, async) → доку тримаєш поруч з артефактом і оновлюєш при змінах.
- **Хостинг:** zeroheight / Supernova — синхронізують доку з Figma-бібліотекою автоматично.
- **Агентний шлях:** Figma MCP-агент може пройтись по бібліотеці й запропонувати описи проперті + флагнути неконсистентний нейминг (перетин з ідеєю I3).

# E4 — Реалістичний контент + empty / edge states

> **Біль:** запитано ×2 в опитуванні (empty states/corner cases + наповнення мокапів). Макет ідеальний на «ідеальних» даних і розсипається на реальних (довге ім'я, порожній стан, помилка).
> **Що зможеш:** правдоподібний контент + набір крайніх випадків що навмисно ламають верстку, щоб зловити проблеми до розробки.
> **Рекомендований інструмент:** 🟢 Claude.ai + Plugin (Content Reel) · ⚡ Figma AI test generator / Figma agent
> **Час:** ≈30 хв

### Етап 1 — Описати екран і поля
**Дія:** Назви екран, перелічи поля/слоти контенту, опиши аудиторію (для локалізації й тону).
**Інструмент:** Claude.ai.
**Промпт:**
```
Я наповнюю макет реалістичним контентом замість lorem ipsum.

Екран: [напр. список замовлень]
Поля: [ім'я, сума, статус, дата, аватар...]
Аудиторія / ринок: [напр. українські користувачі, b2b]
Скільки записів треба: [напр. 8]
```
**Чекпоінт:** Claude зрозумів структуру полів і ринок (для правильних імен/валют/дат).

### Етап 2 — «Золотий» реалістичний набір
**Дія:** Згенеруй нормальний правдоподібний датасет.
**Інструмент:** Claude.ai.
**Промпт:**
```
Згенеруй [8] реалістичних записів у вигляді таблиці/JSON.
Дані мають виглядати справжніми для [ринок]: реальні патерни імен, правдоподібні суми, коректні формати дат і статусів.
Без жартівливих/тестових значень — це піде в демо.
```
**Чекпоінт:** Дані виглядають як справжні; формати (дата, валюта) відповідають ринку.

### Етап 3 — Edge / empty / error варіанти
**Дія:** Окремо згенеруй те, що ламає верстку — головна цінність.
**Інструмент:** Claude.ai.
**Промпт:**
```
Тепер згенеруй крайні випадки, які найчастіше ламають дизайн:
— дуже довге ім'я / назва (40+ символів)
— дуже коротке / порожнє значення
— дуже велике число і нуль
— найдовший і найкоротший статус
— спецсимволи, емодзі, RTL якщо релевантно
— стан "немає даних" (empty state) — який текст показати
— стан помилки — текст повідомлення

Для кожного поясни одним рядком, що саме воно перевіряє.
```
**Чекпоінт:** Є набір «зламуючих» значень + опис empty/error станів з конкретним текстом.

### Етап 4 — Залити в макет
**Дія:** Перенеси дані в Figma.
**Інструмент:** 🟢 Plugin **Content Reel** (свій кастомний контент) або ручна вставка; альтернатива — **AI Content Filler**.
**Чекпоінт:** Макет заповнений; видно чи витримує довгі значення й порожні стани.

### ⚡ Level-up
- **Figma AI test generator:** генерує error states, permission conflicts, empty states за секунди прямо в Figma.
- **Figma agent (beta, 2026):** «fill with realistic content at scale» — заповнює реальним контентом масово по канвасу.
- **Content Reel:** вбудовані набори (імена, адреси, аватари, телефони) для швидких чернеток.

# E2 — Accessibility / WCAG-рев'ю екрана

> **Біль:** запитано в опитуванні («accessibility check»). A11y роблять «на око» або не роблять; у держ/регульованих проєктах це блокер до розробки.
> **Що зможеш:** список a11y-проблем екрана (контраст, ієрархія, тач-таргети, фокус, alt-text) з фіксами, за severity.
> **Рекомендований інструмент:** 🟢 Claude.ai (vision) + Plugin (Stark/Contrast для точних чисел) · ⚡ власний a11y-плагін на Claude
> **Час:** ≈30 хв

> ⚠️ **Чесність:** AI оцінює контраст зі скріна приблизно — піксельні кольори може зчитати неточно. Точні числа бери з плагіна або по hex. AI сильний у **контекстних** проблемах (ієрархія, зрозумілість, alt-text), число-в-число контраст — за плагіном.

### Етап 1 — Підготувати екран і контекст
**Дія:** Скрін екрана + хто аудиторія, де використовується.
**Інструмент:** Claude.ai (встав скрін).
**Промпт:**
```
Ти accessibility-спеціаліст. Зроби a11y-рев'ю цього екрана за WCAG 2.2 AA.

Контекст: [для кого продукт, мобільний/десктоп]
[встав скрін]

Спочатку перелічи, що бачиш на екрані (елементи), щоб я звірила що ти все зчитав правильно. Тільки потім аналіз.
```
**Чекпоінт:** Claude правильно перелічив елементи екрана (інакше аналіз буде про не те).

### Етап 2 — Контраст і колір
**Дія:** Перевір контрастні пари.
**Інструмент:** Claude.ai + звірка плагіном.
**Промпт:**
```
Перевір контраст тексту й фону. Пороги WCAG:
— звичайний текст AA: 4.5:1
— великий текст (≥24px / ≥19px bold) AA: 3:1
— AAA: 7:1

Для кожної пари дай приблизний коефіцієнт і вердикт pass/fail.
Познач, які значення треба перевірити точно в плагіні (бо зі скріна неточно).
```
**Чекпоінт:** Є список пар з вердиктами; сумнівні позначені «перевірити в Stark/Contrast».

### Етап 3 — Ієрархія, тач-таргети, фокус, alt-text
**Дія:** Контекстні перевірки (тут AI найсильніший).
**Інструмент:** Claude.ai.
**Промпт:**
```
Тепер перевір:
— візуальну ієрархію: чи зрозумілий головний елемент / порядок читання
— розміри інтерактивних елементів (мінімум 44×44px тач-таргет)
— чи видно стан фокусу для клавіатурної навігації
— alt-text: запропонуй опис для кожного значущого зображення/іконки
— чи не передається сенс лише кольором (напр. помилка тільки червоним)
```
**Чекпоінт:** Є зауваження по кожному пункту + запропоновані alt-тексти.

### Етап 4 — Фікс-ліст за severity
**Дія:** Зведи в пріоритезований список.
**Інструмент:** Claude.ai.
**Промпт:**
```
Зведи всі знахідки в таблицю: Проблема | Severity (blocker/major/minor) | Який WCAG критерій | Конкретний фікс.
Відсортуй за severity. Прибери все, в чому ти не впевнений — краще менше, але точно.
```
**Чекпоінт:** Таблиця фіксів, відсортована; blocker'и зверху.

### ⚡ Level-up
- **Stark** (Figma plugin): повний a11y-набір — контраст, симуляція зору, alt-text, focus order, тач-таргети, WCAG 2.1/2.2. Детерміновані числа.
- **Contrast / Corpowid** — легші плагіни тільки на контраст.
- **Власний плагін:** дехто будує свій a11y-плагін на Claude — детерміновані WCAG-перевірки + контекстний аналіз від Claude (перетин з механікою «зроби свій інструмент»).

# I2 — Генератор усіх станів компонента

> **Біль:** «дизайн-система ×4» + «empty states» в опитуванні; резонує з історією Ані на /calibrate (4 стани завантаження вручну). Малювати кожен стан variants+auto-layout — години.
> **Що зможеш:** матриця всіх станів + живий HTML-прев'ю, де стани реально перемикаються.
> **Рекомендований інструмент:** 🟢 Claude.ai · ⚡ Figma Make / Figma variants
> **Час:** ≈45 хв

### Етап 1 — Описати базовий компонент
**Дія:** Скрін або опис базового стану + поведінка.
**Інструмент:** Claude.ai.
**Промпт:**
```
Я хочу згенерувати всі стани компонента.

Компонент: [напр. Input field / Card / Button]
Базовий вигляд: [встав скрін або опиши]
Поведінка: [що відбувається при взаємодії]

Які стани цьому компоненту потрібні? Запропонуй повний список і пояснень навіщо кожен.
```
**Чекпоінт:** Claude запропонував перелік станів з обґрунтуванням (а не загальний шаблон).

### Етап 2 — Матриця станів (специфікація)
**Дія:** Опиши кожен стан конкретно.
**Інструмент:** Claude.ai.
**Промпт:**
```
Для кожного стану (default, hover, focus, active, disabled, error, loading, empty, filled) опиши:
— що візуально змінюється (колір, бордер, іконка, текст)
— коли спрацьовує (тригер)
— який мікрокопі/повідомлення показати (для error/empty)

Формат: таблиця. Використовуй токени якщо я їх дам, інакше познач [token].
```
**Чекпоінт:** Таблиця станів; для error/empty є конкретний текст.

### Етап 3 — Живий HTML-прев'ю
**Дія:** Згенеруй файл, де стани перемикаються.
**Інструмент:** Claude.ai.
**Промпт:**
```
Зроби один .html файл, де всі стани компонента показані й перемикаються кнопками зверху.
Стек: Tailwind CDN, vanilla JS, нульові залежності. Світла й темна тема.
Loading — з реальною анімацією, error/empty — з текстом зі специфікації.
Спочатку покажи один стан, переконайся що працює, потім додавай решту.
```
**Чекпоінт:** HTML відкривається в браузері, кнопки перемикають стани, loading анімується.

### Етап 4 — Перенести в Figma / віддати в код
**Дія:** Відтвори як variants або передай як референс розробнику.
**Інструмент:** Figma (variants) або хендоф.
**Чекпоінт:** Або є набір variants у Figma, або лінк на HTML як живий референс (як зробила Аня).

### ⚡ Level-up
- **Figma Make:** будує інтерактивні стани прямо в Figma з документацією поведінки.
- **AI Component Documentation Generator:** драфтить стани (empty/loading/error) як частину доки (перетин з D1).
- **Figma variants + агент:** агент може розкласти стани по properties.

# E1 — Дизайн-критика / евристичний аудит

> **Біль:** «дизайн-критика» + «ревью на консистентність» в опитуванні. Критика «на око», без структури, залежить від настрою рев'юера.
> **Що зможеш:** структурований first-pass по 10 евристиках Нільсена + severity — як стартова точка для **твого** судження, не заміна.
> **Рекомендований інструмент:** 🟢 Claude.ai (vision) · ⚡ Heurio (командна евристика)
> **Час:** ≈30 хв

> ⚠️ **ЧЕСНІСТЬ — читати обов'язково.** Дослідження NN/g (Nielsen): AI зі скріншотів ловить лише **~24% юзабіліті-проблем** (пропускає 76%), і з його редизайн-порад **тільки 19% корисні**, 72% марнують ресурс, 9% шкодять — у середньому ~11 поганих порад на скрін. AI **не бачить флоу між екранами**. Тому E1 — це **генератор гіпотез і структури**, а не вердикт. Обов'язково: людина валідує + парний user testing. Це не слабкість продукту, а чесна рамка — і ми так її і подаємо.

### Етап 1 — Підготувати скрін і завдання користувача
**Дія:** Скрін + що користувач має зробити на цьому екрані.
**Інструмент:** Claude.ai.
**Промпт:**
```
Я роблю евристичну оцінку екрана. Спочатку звіримось.

[встав скрін]
Завдання користувача на цьому екрані: [напр. оформити замовлення]

Опиши, що ти бачиш і який, на твою думку, основний шлях користувача. Я підтверджу або скоригую перед аналізом.
```
**Чекпоінт:** Claude правильно зрозумів екран і ціль користувача.

### Етап 2 — Прогін по 10 евристиках
**Дія:** Структурований аналіз.
**Інструмент:** Claude.ai.
**Промпт:**
```
Прогони екран по 10 евристиках Нільсена. Для кожної:
— чи є проблема (так/ні/н.д.)
— якщо так: опис + severity (blocker/major/minor) + конкретна пропозиція

Евристики: 1) видимість статусу 2) відповідність реальному світу 3) контроль і свобода 4) консистентність і стандарти 5) запобігання помилкам 6) розпізнавання замість згадування 7) гнучкість 8) мінімалістичний дизайн 9) допомога з помилками 10) документація/допомога.

Будь стриманим: якщо не впевнений — пиши "потребує перевірки", не вигадуй.
```
**Чекпоінт:** Структурована таблиця по 10 евристиках; сумнівне позначено.

### Етап 3 — Валідація людиною (критичний крок)
**Дія:** Сама пройдись по списку й відсій галюцинації / неактуальне.
**Інструмент:** ти (+ за бажанням колега).
**Промпт (опційно, для тиску на якість):**
```
Постав під сумнів кожну свою знахідку: які з них ти вивів зі скріна напевно, а які — припущення про поведінку якої не видно? Познач другу групу окремо.
```
**Чекпоінт:** Лишились тільки знахідки, які ти підтвердила. Решта — у «гіпотези для перевірки тестом».

### Етап 4 (опц.) — Перетворити на командний чеклист
**Дія:** Зведи валідоване в чеклист/дискусію.
**Інструмент:** Claude.ai → Notion/Figjam.
**Чекпоінт:** Є чеклист, який можна винести на дизайн-рев'ю.

### ⚡ Level-up
- **Heurio** (Chrome extension): командна евристична оцінка на живому продукті — візуальні коментарі прямо на сайті/в апці, кілька рев'юерів.
- **Парний user testing:** евристика + 3-5 живих тестів ловить набагато більше, ніж будь-що з AI самостійно (рекомендація NN/g).

# P1 — Параметричний дизайн (плейграунд варіантів)

> **Біль:** виробляти десятки варіантів одного дизайну руками (банери в усіх розмірах, формати реклами, соцмережі, email-шаблони) — години механіки. І ще гірше — перевірити, чи дизайн витримує **реальний контент** і **різні вьюпорти**, не намалювавши кожну комбінацію окремо.
> **Що зможеш:** зібрати маленький **плейграунд** (один HTML-файл), де параметри (розмір, копі, тема, контент, вьюпорт) перемикаються живими контролами — і одразу видно всі комбінації + як це поводиться на реальних даних.
> **Рекомендований інструмент:** ⚡ Claude Code (генерує робочий інструмент, не картинку)
> **Час:** ≈60–90 хв на першу версію

> 📍 **РЕАЛЬНИЙ ДОСВІД (Vlad, banner playground).** Це не теорія — я це зробив. Зібрав у Claude Code однофайловий плейграунд для стрес-тесту CMS-банера (Casino + Sportsbook). Параметричні контроли: вьюпорт (1200/1440/1920 з ре-скейлом), девайс (mobile/desktop), вертикаль (casino/sportsbook) — і під кожну комбінацію свій стан лейауту; **розумна типографіка** (розмір шрифту сам адаптується під довжину контенту через `clamp()` + min/max); завантаження власних ассетів + редактор зображення (fit/scale/позиція); фон (solid/gradient/картинка); карусель (кількість банерів, скільки видно, peek, autoplay, розміщення T&C); прев'ю «один банер / кілька одразу»; і навіть **page context** — завантажуєш скріни сторінки навколо банера, щоб бачити його в реальному оточенні. Задеплоїв через GitHub Pages за паролем. **Що здивувало:** AI швидко зібрав каркас, але параметрична логіка на краях вимагала багатьох ітерацій — фон не рендерився при завантаженні, стан не синхронізувався при перемиканні вертикалі, оверлей-картинка чіплялась не до того кута. Тобто каркас — швидко, але «розумну» поведінку треба доводити руками разом з AI. Це жива ілюстрація тези «AI = найзеленіший стажер».

### Етап 1 — Описати простір параметрів
**Дія:** Випиши, що саме варіюється і в яких межах. Це міні-PRD інструмента.
**Інструмент:** Claude Code (або спершу Claude.ai щоб структурувати).
**Промпт:**
```
Я хочу зібрати параметричний плейграунд для [тип артефакту, напр. промо-банер].

Що має варіюватись (параметри):
— розміри/формати: [напр. 1200/1440/1920, mobile/desktop]
— контент: [заголовок, опис, CTA, бейдж...]
— візуал: [кольори фону, тема, завантаження ассетів]
— [інші осі варіації]

Це POC-інструмент для мене, не продакшн. Спочатку запропонуй найпростішу архітектуру (один файл? стек?) і постав запитання, де межі параметрів неясні.
```
**Чекпоінт:** Є список параметрів з межами + запропонована проста архітектура (для банерів — один HTML-файл, vanilla JS, без build).

### Етап 2 — Згенерувати кістяк плейграунда
**Дія:** Попроси робочий однофайловий інструмент з контролами.
**Інструмент:** Claude Code.
**Промпт:**
```
Збери один HTML-файл (HTML+CSS+vanilla JS, без фреймворків і build-кроку):
— ліва панель параметричних контролів (слайдери/інпути/сегменти під кожен параметр)
— жива область прев'ю праворуч, що реагує миттєво
— стан тримай в одному JS-об'єкті `state`, рендер — функцією від state

Спочатку зроби 2-3 базові параметри робочими end-to-end, покажи що оновлюється, і тільки потім додавай решту.
```
**Чекпоінт:** Файл відкривається в браузері; зміна контрола одразу змінює прев'ю.

### Етап 3 — «Розумні» параметри
**Дія:** Додай поведінку, яка робить інструмент справді корисним (а не просто перемикач).
**Інструмент:** Claude Code.
**Промпт:**
```
Додай розумну поведінку:
— типографіка, що адаптується під довжину контенту (clamp() з min/max, які я можу налаштувати)
— завантаження власних ассетів (FileReader) + базовий редактор: fit contain/cover, масштаб, позиція X/Y
— теми/кольори фону (solid + gradient) зі свотчами
— перемикач вьюпорта/девайса, що ре-скейлить прев'ю

Кожну фічу додавай окремо й давай мені перевірити перед наступною.
```
**Чекпоінт:** Текст не ламає верстку на довгому контенті; ассети вантажаться; вьюпорт перемикається.

### Етап 4 — Стрес-тест реальним контентом (зв'язок з E4)
**Дія:** Прожени через реальні дані й крайні випадки.
**Інструмент:** Claude Code + датасет з кейсу **E4**.
**Промпт:**
```
Дай мені швидко прогнати крайні випадки: найдовший заголовок, порожні поля, найбільше число, найкоротший CTA, кілька варіантів одразу.
Де верстка ламається — запропонуй fix параметра (не хардкод).
```
**Чекпоінт:** Видно, які комбінації ламаються, і це фікситься через параметр, а не милицю.

### Етап 5 — Ітерація, збереження, деплой
**Дія:** Дороби, додай збереження пресетів, виклади як лінк.
**Інструмент:** Claude Code → GitHub Pages.
**Промпт:**
```
Додай: збереження/завантаження стану (localStorage + export/import JSON), і підготуй до деплою на GitHub Pages.
Якщо треба — простий клієнтський пароль-гейт.
```
**Чекпоінт:** Є публічний лінк, стан зберігається між сесіями, можна шерити команді.

### ⚡ Level-up
- **Пресети-вертикалі:** окремий стан параметрів під кожен контекст (як casino/sportsbook у реальному кейсі) з резолвером `cfg()`.
- **Page context:** завантаження скрінів оточення, щоб бачити артефакт у реальному середовищі.
- **Baked default state:** зашити дефолтний стан (з base64-ассетами) прямо у файл, щоб інструмент відкривався вже наповненим.
